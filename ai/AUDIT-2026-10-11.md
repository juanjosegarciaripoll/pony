# 1. Shared mutable state mistaken for per-thread state

**The pattern.** State that describes *one flow of control* — how deep
we are in a transaction, which root is active — is stored where *the
whole process* can see it. It reads correctly in a single-threaded
test and silently crosses threads in production. The tell is an
instance attribute (or a module global) whose name contains "current",
"depth", "active" or "pending".

**How to spot it.** Ask of every mutable attribute: *if two threads
were inside this method at once, would each need its own copy?* If yes,
it belongs in `threading.local()` or in the call stack, not on `self`.

### 1.1 Batch state shared across threads

- [x] **`_batch_depth` / `_batch_writes` are instance attributes** — `src/pony/index_store.py:293-300`, `:355-414` · commit `14727e3` · **data + trust** · `[V]`

  They used to be `threading.local()`. `connection()` now holds
  `self._lock` only to bump the counter, not across the block, so two
  threads that each open a `connection()` share one transaction and one
  depth counter. Reproduced:

  ```
  B's write returned normally
  A raised (as sync.py would catch): thread A's folder failed
  B's row after A's rollback: None
  ```

  `insert_message` returned, the `Outcome` said it worked, the row is
  gone. The reverse direction is equally live: a UI-thread write that
  raises calls `conn.rollback()` on the shared connection and discards
  up to 499 of the sync's already-applied operations while the sync
  reports success.

  The thread topology exists in both front ends: `POST /action/*` runs
  in a 40-worker thread pool over one repository (`web/app.py:786`,
  `cli.py:2866-2886`), and the TUI runs sync and list actions as
  workers beside `PeriodicSync` (`tui/screens/main_screen.py:548,567`).

  Sharpest consequence: `mailbox_actions._move_in_place` renames the
  mirror file *first*, then rewrites the row inside `connection()`.
  Lose that write and the file is in Archive while the index points at
  the source — `get_message_bytes` then raises on a message the reader
  said it archived.

  **Fix:** put the depth and the write count back in `threading.local()`
  and give each thread its own connection, keeping the per-500 commit.
  `src/chronos/index_store.py:226-258` still does exactly this and is
  the model to copy.

- [x] **`connection()`'s `finally` assigns instead of decrementing** — `src/pony/index_store.py:389-391` · **trust** · `[V]`

  The outermost block does `self._batch_depth = 0` while a nested
  entrant does `-= 1`. Out-of-order exit (two threads, so the order is
  the scheduler's) leaves `-1`, after which `outermost` is never true
  again and **no `connection()` block commits or rolls back for the
  life of the process**. Writes still land one statement at a time, so
  nothing fails — the batching is simply off, silently, and the
  rollback guarantee the docstring promises at `:285` is gone.

- [x] **Reads count toward the 500-write commit** — `src/pony/index_store.py:410-414` · **polish** · `[A]`

  `_use()` increments `_batch_writes` on every call, including reads.
  "Commit every 500 writes" is really "every 500 calls", so a user
  scrolling during a sync can be the thing that ends the sync's
  transaction mid-folder.

- [x] **`close()` yanks the connection out from under a live batch** — `src/pony/index_store.py:346-355` · **polish** · `[A]`

  Another thread's in-flight batch gets
  `ProgrammingError: Cannot operate on a closed database`. Also:
  `close()` has **no caller anywhere in `src/pony`**, so the mail index
  relies on `__del__` to commit its last partial batch, and `run_web`'s
  `finally` (`cli.py:2910`) never calls it.

### 1.2 A process-wide global where a parameter belongs

- [ ] **`chronos.paths.activate()` is a mutable module global** — `src/chronos/paths.py:92-99` · **polish** · `[R]`

  Against `docs/architecture.md:729` ("Avoid hidden globals; pass
  dependencies explicitly"). `tests/conftest.py` and
  `tests_calendar/conftest.py` both call it with different roots at
  import time; under `-n auto --dist loadfile` a worker that takes
  files from both directories gets whichever imported last. Benign
  today (both are temp dirs) and exactly what the "do not write a test
  that depends on anything another file did" rule is about.

  Left open after reading it: `active()` has 29 call sites across 11
  modules, including `chronos/config.py`, `chronos/domain.py` and both
  `main_screen.py` files. Threading a `CalendarPaths` through all of
  them is the fix, and it is a refactor of the calendar's whole
  bootstrap rather than an edit — not something to land beside
  unrelated defect fixes.

- [x] **`MainScreen._save_last_view` writes session-wide state during tests** — `src/chronos/tui/screens/main_screen.py` → `active().tui_state_file` · **polish** · `[A]`

  Each `Pilot` test inherits the previous one's view. Visible in the
  assertion it forced: `tests_calendar/test_tui_flows.py:1183` asserts
  `event_list.has_focus or timeline.has_focus` with a comment admitting
  why.

  Left open after reading it: the persistence is the feature —
  `_load_last_view` is meant to outlive the process — so there is no
  defect in the source to fix. What leaks is test isolation, and the
  only fix is per-test isolation in the calendar's own suite (an
  autouse fixture in `tests_calendar/conftest.py` re-activating
  `chronos.paths` per test, which is the same lever §1.2's first item
  needs) or taking the initial view as a collaborator on `TuiServices`.
  Either one lands in `tests_calendar/test_tui_flows.py` to be worth
  anything — the assertion above is what it would tighten — and it
  cannot be *shown* by a test that fails without it: a test asserting
  "this session opens in AGENDA" passes on its own and fails only after
  another file ran, which is the rule it is trying to enforce. So the
  box stays unticked on purpose.

  Closed by the lever the note names: `tests_calendar/conftest.py` now
  activates a calendar root per test, so no test inherits the view
  another left in `tui_state`.  The source is unchanged, because the
  persistence is the feature.

  The assertion it forced is tightened: a fresh session opens on the
  agenda, so `test_primary_view_widget_has_focus_on_mount` requires the
  event list to have focus and the timeline not to, where it used to
  accept either.  That is the test that fails without the fixture,
  which is as close as this gets -- a test for isolation cannot fail on
  its own, only after another file has run.
  `tests_calendar/test_paths.py::PerTestRootTest` checks the lever
  directly: the activated root is not the session's, and no view file
  is inherited.

# 2. The screen answers a question the model should have been asked

**The pattern.** A front end holds a piece of context — the open
folder, the top of the screen stack, the first row of a list — and uses
it as a *proxy* for the thing the operation is actually about. It works
whenever the proxy happens to agree with reality, and the cases where
it does not are exactly the interesting ones: search results, modals,
multi-select.

**How to spot it.** When a screen reads its own attribute to decide
something about a *specific object*, ask the object instead. Five of
the eight verified Textual defects are this one mistake.

### 2.1 Asking the folder instead of the message

- [x] **`e` on a received message opens it as a draft and then destroys it** — `src/pony/tui/screens/main_screen.py:906-918`, `:1473` · **data** · `[V]`

  `check_action` gates `edit_draft` on `_in_drafts_folder()`, which
  asks whether the *last-selected folder* holds drafts. Search results
  span folders and `_run_search` never updates `_current_folder_ref`,
  so `e` is live on an INBOX hit. `compose_from_draft` passes the
  message as `source_draft`, and `delivery.file_draft` /
  `deliver_message` retire whatever they are handed without checking it
  is a draft. With a UID the row is marked TRASHED and the next sync
  expunges it server-side.

  The browser asks the right question (`web/compose.py:204`,
  `holds_drafts` on the message's own folder), so the terminal is the
  broken half of a question the model was supposed to own.

  **Fix:** `holds_drafts` on `msg`'s own folder inside
  `compose_from_draft`, **and** a guard in `file_draft` /
  `deliver_message` refusing a `source_draft` that is not in a Drafts
  folder. The second half is what turns this from wrong into
  destructive.

### 2.2 Asking the screen stack instead of holding a handle

- [x] **F1 during sync planning strands the dialog with no way out** — `src/pony/tui/screens/main_screen.py:580`, `:606`; `src/pony/tui/screens/sync_confirm_screen.py:195` · **time** · `[A]`

  `DialogScreen` does not set `INHERIT_BINDINGS = False`, so app-level
  `f1`/`f2` fire over the sync modal. Both completion handlers guard on
  `isinstance(self.app.screen, SyncConfirmScreen)`, false while help is
  on top, so `show_plan` never runs. `on_key` returns early while
  `_planning`, so `escape`, `q` and `n` are all swallowed. Only
  ++shift+q++ escapes, and the scheduler slot stays claimed for the
  rest of the session, so background sync is dead too.

  **Fix:** reach the dialog through a held reference or
  `self.app.get_screen`, and let `on_key` dismiss while planning.

### 2.3 Asking the first target instead of each target

- [x] **Marks spanning folders are handed one source folder** — `src/pony/tui/screens/main_screen.py:1019` · **data** · `[A]`

  `source = self._folder_ref_from_summary(targets[0])` is passed for
  *all* targets. In search results the marks can span folders.
  Reproduced with one INBOX and one Work message marked, pressing `A`:

  ```
  INBOX msg -> ('Archive', PENDING_MOVE)
  Work  msg -> ('Work', ACTIVE)          # not archived
  notice: error       | Failed to move message in local mirror.
  notice: information | Archived to Archive.
  ```

  Two contradictory toasts, one message silently left behind, and the
  marks are cleared so there is nothing to retry.

  **Fix:** group targets by their own folder in `_act_on_targets`, or
  let `move_messages`/`archive_messages`/`copy_messages` take the
  source per message.

- [x] **Any list action throws away the search** — `src/pony/tui/screens/main_screen.py:1019` → `_reload_folder` · **time** · `[A]`

  `_reload_folder` calls `load_folder`, which exits search mode:

  ```
  search rows: ['zzq one'] | in_search: True  | title: 'Search: zzq'
  after archive:  ['other mail'] | in_search: False | title: 'Messages'
  ```

  Archive, trash, flag, mark-unread, move and replying all do it, so
  triage from a search is one search per message. The browser keeps the
  query in the URL. Related: when `source != _current_folder_ref` the
  panel and the screen disagree about which folder is open, and the
  From/To column is chosen from the wrong one.

  **Fix:** hold the query and its scope on the screen and reload
  whichever of folder/search is on screen.

### 2.4 The refreshed row list forgets which row is open

- [x] **After any successful action the browser acts on the wrong message** — `src/pony/web/app.py:295-301`, `static/pony.js:36-37`, `:253-272` · **data** · `[V]`

  `_rows_fragment` calls `mail_view.rows(...)` without `open_id`, which
  defaults to `None`, so the fragment carries no `aria-selected` and no
  `.open`. `refresh()` replaces `#rows` with it and calls
  `select(selectedRow())`; `selectedRow()` falls back to `rows()[0]`.
  Open message 3 of 3, press `u`, press `A`:

  ```
  posts: [ /action/mark_unread  id=3
           /action/archive      id=1 ]
  selectedAfter: "1"
  ```

  Archive, Trash and Move are destructive. The reader also loses every
  visual cue about which row is open.

  **Fix:** carry the open id in `mailParams()`, pass it to
  `mail_view.rows(open_id=…)`, and have `targets()` prefer
  `document.body.dataset.message` on the reader surface — which is
  exactly what `tests/web_helpers.py:_selected` already does. See
  [§13.2](#132-the-helper-is-more-correct-than-the-code-it-simulates).

- [x] **"Delete marked" with nothing marked deletes the auto-selected row** — `src/pony/web/contacts.py:296-303`, `static/pony.js:68-72` · **data** · `[A]`

  `targets()` falls back to the selected row, and `start()`
  auto-selects `rows()[0]` on load. So tapping "Delete marked" on a
  freshly loaded contacts list deletes the first contact. A bulk
  operation whose label says "marked" should refuse when nothing is
  marked, rather than guessing. See also
  [§9.1](#91-irreversible-in-one-front-end-confirmed-in-the-other).

# 3. A predicate on the wrong side of a boundary

**The pattern.** A filter is applied in Python *after* the database has
already truncated, sorted or aggregated. The code reads as if the two
steps compose; they do not, because `LIMIT` is not distributive over a
later filter.

**How to spot it.** Any `[x for x in store.query(...) if ...]` where
`query` takes a `limit`, or any aggregate computed before a narrowing.

### 3.1 Narrowing after the limit

- [x] **A folder-scoped search in a large account returns nothing** — `src/pony/tui/screens/main_screen.py:835` and `src/pony/web/mail.py:348-368` · **trust** · `[A]`

  Both post-filter by folder after `index.search(...)` has applied its
  account-wide `LIMIT 500` (`index_store.py:1000`). Reproduced with 1
  matching message in INBOX and 520 in Archive:

  ```
  rows returned by index.search: 500
  after the screen's folder post-filter: 0
  ```

  The browser's variant shows "Nothing found." The existing test
  (`tests/test_main_screen_messages.py:471`) uses two messages and
  cannot see it.

  **Fix:** give `IndexRepository.search` a `folder_name` and push the
  scope into SQL. (Or, in the browser's case, drop the narrowing to
  match the terminal, which does not narrow at all.)

### 3.2 Restricting the loop but not the query

- [x] **`populate_alarms` filters the masters and still reads the whole window** — `src/chronos/recurrence.py:237-250` · commit `7b6e0ee` · **time** · `[R]`

  Already fixed in `7b6e0ee`: the occurrence read now passes
  `uids=uids` and `query_occurrences` applies it in SQL (chunked, with
  the empty set short-circuited). A spy test pins the kwarg, since the
  output is identical either way and only the row count differs.

  `masters` is reduced to the changed UIDs; the occurrence read above
  it is unconditional. The fix from the stall reached the loop and not
  the query.

- [ ] **`query_occurrences` still visits every component** — `src/chronos/index_store.py` · **time** · `[R]`

  Known and unfixed from the sync-performance work. Left open
  deliberately: `7b6e0ee` gave the query a `uids` filter, which closes
  the alarm-rebuild path above, but a *window* query cannot use
  `ix_occurrences_range` at all — the lower bound sits inside a `CASE`
  and no single range is both "starts before the window ends" and
  "ends after it begins". Serving it needs a denormalised column with a
  maximum-duration bound, or an R-tree: a schema change with a
  migration, which is a redesign rather than a repair. `7b6e0ee`'s own
  message says so.

# 4. One rule, two copies, drifted

**The pattern.** The same decision — is this a Sent folder, is this an
all-day span, what is a safe filename — is written in two places. They
agree on the day they are written. Later, one is fixed. The program now
holds two answers to one question and takes whichever the call site
happens to reach.

This is the largest class in the codebase: roughly twenty rules exist
in two copies, and nine of them now disagree in ways a user can feel.
Three were made *worse* yesterday, because `8b2522f` and `ef3ce05` each
unified one side of a pair and left the other.

**How to spot it.** Grep for the constant or the phrase, not the
function name. Two functions with near-identical docstrings in
different modules is the signature.

**The structural fix**, which closes most of this section: move each
shared predicate to the `chronos` side of the dependency arrow and have
`pony` import it. Start with `safe_component`, `is_sent_folder`'s
table, the charset-aware decode, the chunker, and the datetime↔SQL
normaliser.

### 4.1 Copies that disagree, with user-visible consequences

- [x] **A localised Sent folder never receives a copy of anything you send** — `src/pony/delivery.py:201-207` → `src/pony/folder_utils.py:26` vs `:136-158` · **data** · `[V]`

  `record_sent` resolves the folder through `find_folder(names, "Sent")`
  — exact / ends-with / contains on the English word. Sitting in the
  same module is `is_sent_folder`, which folds the leaf name against a
  50-name localised table (`Enviados`, `Envoyés`, `Gesendet`,
  `送信済み`). Measured: `is_sent_folder('Enviados') → True`,
  `find_folder(['Enviados'], 'Sent') → None`.

  So on a Spanish or German server with no explicit `sent_folder`, the
  message list correctly shows the folder as outgoing (it asks
  `is_sent_folder`) and `record_sent` returns
  `Could not find 'Sent' folder` — no local record of anything sent.

  **Fix:** resolve the hint through `is_sent_folder` (and its
  siblings), which is already in the same file.

- [x] **Every non-UTF-8 message is mojibake in the list, and unsearchable by its own words** — `src/pony/message_projection.py:190` · **data** · `[V]`

  `decoded.decode("utf-8", errors="replace")`, ignoring the declared
  charset. Every other decoder in the program consults
  `get_content_charset()`: `message_renderer.py:475-477`, `:485`,
  `:758`, `compose_utils.py:305`. On an `iso-8859-1` message the
  preview reads `Ni�o caf�` where the reader shows
  `Niño café` — and `body_preview` is what the FTS index is built
  from, so those messages cannot be found by their own words.

  Secondary: only `message_renderer.py:477` strips NUL; `:759` is the
  same rule and does not.

- [x] **`calendar edit` converts an all-day event to a timed one** — `src/chronos/views.py:439-458` vs `src/chronos/mutations.py:105-118`, used by `src/chronos/cli.py:1207` · **data** · `[A]`

  `is_full_day` accepts ≥23 h beginning at UTC *or local* midnight;
  `is_all_day_span` requires ≥24 h with *both* ends at UTC midnight. A
  local-midnight all-day event at UTC+2 gives `True` / `False`. The
  grid draws it as a banner, the CLI decides it is not an all-day span
  and rewrites it timed. That is the exact Outlook/Apple case
  `is_full_day`'s docstring was written for.

  `ef3ce05` declared `is_all_day_span` "the only test of a stored span".
  It is not, and the copy it did not unify is the more correct one.

  There is one rule now, and it is that one: `is_all_day_span` takes
  the >= 23 h floor and the "UTC *or* the reader's midnight" anchor, and
  `views.is_full_day` asks it of an occurrence, so what a grid draws as
  a banner is what `calendar edit` keeps as `VALUE=DATE`. The reader's
  zone comes from `ical_parser.local_tzinfo()` rather than a bare
  `.astimezone()`, which is what makes the rule testable in UTC, where
  the two readings are the same.

  Writing it back needed a second fix: `build_event_ics(all_day=True)`
  wrote the *UTC* calendar date, so keeping a local-midnight all-day
  event as `VALUE=DATE` would have moved it to the day before.
  `mutations.all_day_date` picks the date of whichever midnight the span
  begins at, and the end is the start plus the span rounded to whole

# 6. Comparing a normalised value against an unnormalised one

**The pattern.** A value is stored in a canonical form on one path and
in its original form on another, and then compared *textually*. The
comparison is right for the values that happen to already be canonical
and wrong for the rest.

**How to spot it.** Any `=` in SQL against a formatted datetime, a
path, an address or a folder name. Normalise at the single point of
entry, not at each comparison.

### 6.1 Comparing a normalised value against an unnormalised one

- [x] **`find_pending_matches` replaced datetime equality with string equality** — `src/pony/index_store.py:818-855`, `src/pony/sync.py:2666-2690` · commit `e7e0fd3` · **data** · `[A]`

  The old `_rows_matching_projection` compared
  `row.received_at == probe.received_at` in Python — semantic, tz-agnostic.
  The new SQL compares `received_at = ?` against `received_at.isoformat()`.
  `_row_params` stores the header's own offset (`:155`) and
  `_indexed_message_from_row` reads it back `.astimezone(UTC)` (`:2192`),
  so a row written straight from a projection keeps `+02:00` and a row
  read back and rewritten is normalised to `+00:00` — while the probe
  always carries the header's offset.

  ```
  after one read+rewrite (stored as +00:00 now)
    probe with the ORIGINAL projection datetime (+02:00): 0
    python-level comparison would have matched: True
  ```

  Every UID-bearing row is rewritten on each flag sync
  (`sync.py:2017-2024`). So: a UIDVALIDITY reset on a flag-synced
  folder, a message whose `Date:` is not UTC, and a Message-ID that
  does not settle it → the row is not adopted, a duplicate is inserted,
  and the orphan becomes a `PushAppendOp`. Verbatim the failure the
  fallback's own comment says it exists to prevent.

  **Fix:** store `received_at.astimezone(UTC).isoformat()` in
  `_row_params` and compare against the same normalisation — as
  `chronos/index_store.py:946-949` already does.

- [x] **No UTC normaliser in the mail index at all** — `src/pony/index_store.py` · **data** · `[R]`

  The read side is spelled two ways: with `.astimezone(UTC)` at
  `:1210, 2168, 2171, 2192, 2243, 2258, 2273`, and **without** it at
  `:1104` and `:1129` (`FolderSyncState.synced_at`). The write side
  never normalises. It works only because three independent boundaries
  guarantee UTC — and `purge_expired_trash`'s lexical
  `trashed_at <= cutoff` (`:683-700`) and the `received_at DESC` index
  both depend on that. One normalising helper on write closes this and
  the item above.

- [x] **`uid_of` cannot read a filename another MUA has flagged** — `src/pony/storage.py:1135` · **data** · `[A]`

  `_UID_SUFFIX_RE` is `,V=(\d+),U=(\d+)\Z`. Pony writes its own flag
  suffix as `!2,S` and forces `Maildir.colon = "!"`, so Pony's files
  parse. Any file the *other* client flagged carries the standard
  `:2,S`:

  ```
  '…,V=99,U=200:2,S' -> uid_of: None
  '…,V=42,U=301'     -> uid_of: (42, 301)
  epoch vote = 42
  ```

  So on a tree another MUA has touched — the case
  `docs/architecture.md:165-169` explicitly invites — `pony reindex`
  indexes the current-epoch messages as local-only *and* stamps the
  folder's watermark from the only file that still parses.

  **Fix:** tolerate a trailing `:2,…` / `!2,…` info section. One regex,
  and it decides whether a shared Maildir can be reindexed at all.

# 7. Guards with inverted, absent or off-by-one conditions

**The pattern.** A safety check exists, and the condition on it is
wrong in the direction that matters: it fires when the situation is
harmless and stays quiet when it is not. Worse than no guard, because
the guard's presence is taken as proof the case was considered.

**How to spot it.** Write out the case the guard was added for, in
words, and read the condition against it. Then check the boundary.

### 7.1 Inverted

- [x] **`pony reindex`'s warning is silent in exactly the case that needs it** — `src/pony/cli.py:1565` · commit `3b2f473` · **trust** · `[A]`

  every message becomes an upload candidate — `with_uid` is 0 and no
  warning prints. That is the state of any mirror written before the

- [x] **The mass-push confirmation asks the opposite of what happens** — `src/pony/sync.py:1766-1783`, `:2332-2345`; `src/pony/cli.py:1039-1086` · **trust** · `[A]`

# 8. Missing trust boundaries

**The pattern.** An endpoint, a header or a payload is treated as
trustworthy because of where it *usually* comes from. Browsers do not
work that way: a page the user opens anywhere can speak to a loopback
port, and a message body is attacker-supplied markup.

**How to spot it.** For each route, name the attacker position and what
they get. If the answer begins "but they'd have to be on the network",
check whether a browser can reach it from any page — it can.

### 8.1 No CSRF defence at all under `--no-token`

- [x] **Any web page the user opens can delete the mail, send mail as them, and kill the process** — `src/pony/web/app.py:226-240`; no origin check anywhere in `src/pony/web` · **data** · `[V]`

  `POST /action/<name>` has no `Origin` or `Sec-Fetch-Site` check (grep:
  zero hits). When `services.token is None`, `_check_token` returns
  `None` and every action runs. Reproduced from a genuinely cross-site
  origin in headless Chromium:

  ```
  token=None:    submitted=True  shutdown_called=True  inbox_before=[1] inbox_after=[]
  token='tok3n': submitted=True  shutdown_called=False inbox_before=[1] inbox_after=[1]
  ```

  The attacker never reads a response and does not need to. `/compose`
  is a plain `method="post"` form, so the same page can send mail; and
  `/compose/attachment` accepts arbitrary bytes.

  The address is not protection: the default `127.0.0.1:8730` is
  reachable from the user's own browser whatever the network does, and
  it is a documented constant. `docs/architecture.md` recommends
  `--no-token` on a tailnet, so this is the configuration the design
  points at.

  **The token case is refused only by `samesite="strict"`** on the
  cookie (`app.py:256`), whose comment frames it as phone convenience.
  One edit to `"lax"` and this applies to the default configuration.

  **Fix:** refuse every state-changing request whose `Sec-Fetch-Site`
  is `cross-site` (or whose `Origin` is present and not the server's
  own), in `_handler`, independent of the token. Three lines, and it
  closes `/action/*`, `/compose`, `/compose/attachment` and
  `/contacts/edit` at once. Keep `samesite="strict"` and say in the
  comment that it is security, not convenience.

### 8.2 CSP omits the directives that do not inherit

- [x] **A hostile message can phish from Pony's own origin** — `src/pony/web/app.py:343-350` · **data** · `[A]`

  ```
  default-src 'none'; img-src data:; style-src 'unsafe-inline'
  ```

  `form-action` and `base-uri` **do not fall back to `default-src`**
  (CSP3). A `<form action=…><input name=pw>` in a `text/html` message
  submitted successfully in Chromium:

  ```
  report: {'formFound': True, 'framePath': '/__sink?pw=secret'}
  sink hit: [{'pw': 'secret'}]
  ```

  `build_browser_html` passes `<script>`, `<form>`, `<iframe>`,
  `<object>`, `<base href>`, remote `<img>` and `<svg>` through
  untouched. The CSP blocks the script, the frame, the object and the
  remote image — not the form, and not `<base>`. So a message can
  render a convincing "re-enter your password" form on a page Pony
  serves, one tab from the mailbox. `Referrer-Policy: no-referrer`
  means the attacker does not learn the host; the typed data still
  leaves.

  **Fix:** add `form-action 'none'; base-uri 'none';
  frame-ancestors 'none'`, and consider `sandbox allow-popups`.

### 8.3 Smaller boundary defects

- [x] **The token gate raises on a non-ASCII token** — `src/pony/web/app.py:238` · **polish** · `[A]`

  `secrets.compare_digest` on `str` raises `TypeError` for non-ASCII:
  `GET /mail?token=%C3%A9` → 500 with a traceback, not 403. No bypass,
  but the one function that must never raise, raises, and it
  distinguishes itself from a normal refusal. Guard with
  `offered.isascii()`.

- [x] **An attachment with a non-Latin-1 filename returns 500** — `src/pony/web/app.py:391-394` · **time** · `[A]`

  `_quotable` strips `"`, `\` and `\r` and nothing else; Starlette then
  encodes `Content-Disposition` as latin-1, so `документ.pdf` raises
  `UnicodeEncodeError` and the attachment cannot be downloaded. `\n`
  survives `_quotable` — the email parser folded it here, so header
  injection did not materialise, but the guard is one layer thinner
  than it looks. **Fix:** RFC 6266 — ASCII `filename=` plus
  `filename*=UTF-8''<percent-encoded>`.

- [x] **Unbounded upload into memory** — `src/pony/web/app.py:443-452` · **time** · `[A]`

  `data = await request.body()` with no size cap. See also
  [§10.3](#103-a-staging-directory-that-is-never-cleaned).

- [x] **`GET /message` changes state** — `src/pony/web/app.py:313` · commit `f3e4071` · **polish** · `[A]`

  Marks `SEEN` on a GET. A prefetch, a link-preview bot, or (under
  `--no-token`) a cross-site `<img src>` marks mail read.

  Already fixed in `f3e4071`: `_opened_by_a_reader` refuses a
  `Sec-Purpose` naming prefetch or prerender, and anything
  `_from_own_page` does not vouch for. The write stays on the GET
  deliberately — opening a message is what marks it read — and
  `test_nothing_but_a_reader_marks_a_message_read` walks all three
  labels the browser puts on the cases that are not a person reading.

- [x] **Reflected notice text** — `/mail?notice=…&severity=error` · **polish** · `[A]`

  Renders attacker-chosen prose inside Pony's chrome with error
  styling. Correctly escaped, so it is a phishing surface rather than
  an XSS one.

  Fixed with the boundary §8.1 installed, since it is the same
  question: `_notices` returns nothing unless `_from_own_page` vouches
  for the request. A `?notice=` is Pony talking to itself across its
  own 303, so same-origin (or an unlabelled client, which is the user)
  is the whole legitimate population.
  `tests/test_web_app.py::test_a_notice_only_comes_from_ponys_own_redirect`
  asks for the same page twice and asserts "Your session expired. Sign
  in again at evil.test" renders for Pony's redirect and not for a
  cross-site link.

**Cleared, and worth recording.** `html.py`'s escaping holds under a
deliberate break-out payload through `From`, `To`, `Cc`, `Subject`, the
HTML body, an anchor's text and href and an attachment filename, in
every page, including inside `value="…"`, `<title>`, `<textarea>` and
`data-*`. `javascript:` cannot reach `_body` (the renderer records only
`http://`/`https://` anchors). The attachment and raw routes are always
`Content-Disposition: attachment` with `nosniff`. The staged-attachment
token is 64 bits from `secrets`, matched against `\A[0-9a-f]{16}\Z`, and
never used as a path. The token itself is 192 bits compared
constant-time. One latent trap: `html._text` uses `escape(quote=False)`,
unsafe inside `<script>`/`<style>` — no call site builds either today;
worth a comment saying so.

# 9. Irreversible work with no confirmation

**The pattern.** The confirmation lives in one front end because that
is where it was first written. The operation then grows a second
caller, which gets the operation without the question.

**How to spot it.** For every `ConfirmScreen` in `tui/`, ask what the
browser does with the same action — and the reverse.

### 9.1 Irreversible in one front end, confirmed in the other

- [x] **Deleting and merging contacts is unconfirmed in the browser** — `src/pony/web/contacts.py:296-303`, `:306-315` vs `src/pony/tui/screens/contact_browser_screen.py:248-262`, `:278-292` · **data** · `[A]`

  noting "merging is irreversible". The browser does neither. Combined

  this is one tap from deleting a contact nobody chose.

- [x] **Deleting an event is unconfirmed in the browser** — `src/pony/web/calendar.py` vs `src/chronos/tui/screens/main_screen.py:388` · **data** · `[A]`

  recoverable.)

- [x] **`Escape` discards a half-written message with no prompt** — `src/pony/web/static/pony.js:~612`, `:556` · **data** · `[A]`

# 10. State that outlives what it describes

**The pattern.** A cache, a watermark or a temp directory records "I
have already done this". The thing it describes is then destroyed by a
different code path, and the record survives to assert something false.

**How to spot it.** For every piece of derived state, ask which
commands destroy its subject — and check each of them clears it.

### 10.1 `reset` leaves the cache that hides what it kept

- [x] **After `pony reset`, a local account's mail is on disk and invisible** — `src/pony/cli.py:2533-2614` (whole-tree path) · **trust** · `[V]`

  The whole-tree reset deletes the index, keeps `LocalAccountConfig`
  mirrors by design, and never touches `<data_dir>/local_scan_state.json`.
  `rescan_local_account`'s fast path skips any folder whose mtime
  matches the stored state (`storage_indexing.py:167-177`) regardless
  of whether the index has rows. Reproduced: 12 local messages →
  `pony reset --yes` → `pony rescan` prints
  `Rescan complete: 0/0 message(s) updated.` with **0 rows**.
  `run_tui`'s startup rescan uses the same stale state, so reopening
  the TUI fails identically.

  Reset's closing line is `Run 'pony sync' for a clean synchronization`
  — and `pony sync` skips local accounts. `rescan --force` or `reindex`
  recover it, and neither is suggested.

  **Fix:** clear `local_scan_state.json` in `run_reset`. One line. The
  per-account path (`_run_reset_account`, `cli.py:2676-2686`) already
  does it correctly and is the model.

### 10.2 A watermark asserting an epoch it cannot honour

- [x] **`rescan` then `reindex` — the obvious recovery order — recovers nothing and still stamps the folder** — `src/pony/storage_indexing.py:330`, `:366-378` · commit `8b36c82` · **data** · `[A]`

  Already fixed in `8b36c82`: `IndexRepository.adopt_uid` gives a
  handle-less row the handle its file carries, `ReindexResult.adopted`
  counts them, and `test_a_rescan_first_still_recovers_every_handle`
  walks the rescan-then-reindex order and asserts the watermark is one
  the index can honour.


  `known` is a storage-key set, so rows a `rescan` already created are
  skipped (`added=0`, every `uid` still `NULL`) — **but the watermark
  is written anyway**, claiming `uid_validity=42, highest_uid=3`. The
  index then asserts an epoch it cannot honour: the next sync sees
  `local_uids = ∅`, re-downloads the whole folder (the one thing
  `reindex` exists to avoid), and plans a `PushAppendOp` per uid-NULL
  row. The docstring's "safe to repeat and safe to point at a partial
  index" is not true of the state it leaves.

  **Fix:** adopt a recovered UID onto an existing `uid IS NULL` row
  instead of skipping it.

- [x] **Rows get `uid=<N>` with `uid_validity=0` while the folder state says 42** — `src/pony/storage_indexing.py:353-363` · **latent** · `[A]`

  `domain.py:410-411` documents `uid_validity` as "the server's
  UIDVALIDITY at the moment `uid` was assigned". Harmless today only
  because nothing reads the field — see
  [§14.3](#143-documented-invariants-nobody-checks).

  Fixed: the epoch travels with the UID. `_ingest_one` takes
  `uid_validity` and sets both fields, and the reindex loop passes the
  epoch it derived for the folder — the same number it stamps into the
  watermark. `tests/test_reindex.py::
  test_a_recovered_handle_carries_the_epoch_it_was_assigned_on` asserts
  `row.uid_validity == 7` and that it equals the watermark's; it read
  `0` before.

- [x] **One `IntegrityError` aborts an entire account's rebuild** — `src/pony/storage_indexing.py` · **data** · `[A]`

  Two files in one folder carrying the same handle → `UNIQUE constraint
  failed` and **0 rows left**. For a disaster-recovery tool that is the
  wrong failure mode: catch per key and report. Note the chain with
  [§1.1](#11-batch-state-shared-across-threads) — a batch rolled back
  by another thread leaves the mirror file written and the row gone, so
  the next sync writes a *second* file with the same `,V=,U=`,
  manufacturing this precondition.

  Fixed by recognising the clash before the insert rather than by
  catching the backend's exception: the loop holds the folder's claimed
  UIDs (`list_folder_uids`, plus whatever this pass assigns) and a
  second file claiming one is logged by name, counted in
  `ReindexResult.conflicts`, and left on disk — the file is still
  there, and it is the stray, not the row. `tests/test_reindex.py::
  test_two_files_claiming_one_handle_do_not_take_the_rebuild_down`
  raised `UNIQUE constraint failed` before the fix and lost every row
  in the account; `tests/test_cli.py` pins the line that reports them.

- [x] **`reindex` cannot recover a single UID from an mbox mirror and does not say so** — `src/pony/storage.py:573-583` · **trust** · `[A]`

  `MboxMirrorRepository.stamp_uid` is a documented no-op ("an mbox key
  is a position and cannot carry a handle"), while
  `pony reindex --help` promises "recovering each message's server
  handle from its filename". Refuse, or warn.

  Warns, and asks the backend rather than the config string: the
  mirror protocol gained `carries_handles` (`True` for Maildir, `False`
  for mbox, beside the `stamp_uid` that is a no-op because of it), and
  `run_reindex` says the keys cannot carry a handle, that every message
  is therefore indexed as local-only, and to run `sync --dry-run`
  first. It proceeds — indexing rows a missing index needs is still
  worth doing — it just stops reporting that as a successful recovery.
  `tests/test_cli.py::
  test_an_mbox_mirror_is_told_it_has_no_handles_to_recover` asserts the
  line.

### 10.3 A staging directory that is never cleaned

- [x] **Uploaded mail accumulates in `$TMPDIR` for the life of the machine** — `src/pony/web/compose.py:58-69` · **time** · `[A]`

  `tempfile.mkdtemp(prefix="pony-web-attachments-")` under
  `@functools.cache` — outside `data_dir`, outside `PONY_ROOT`, and
  never removed: no `atexit`, no cleanup on send, nothing in
  `run_web`'s `finally`. `_forwarded_copy` (`:578`) stages a fresh copy
  on every attempt, so four failed sends of one forward left four full
  copies. Default `TMPDIR` here is `/tmp`, a 955 MB RAM-backed tmpfs.

- [x] **`PONY_ROOT` does not contain an absolute `mirror.path`** — `src/pony/config.py:415-417` (no `contain()`, unlike `data_dir` at `:110`) · **trust** · `[V]`

  `ai/AGENTS.md:79-82` and `docs/index.md:172-175` claim `PONY_ROOT`
  "relocates every directory a run writes to … which is why no test can
  reach a real directory", and `docs/configuration.md:382` tells the
  user to "use absolute for custom locations".
  `src/pony/paths.py:3` ("Everything Pony writes lives under one
  directory") is wrong on this and on the staging directory above.

  Fixed: `_parse_mirror` now returns `contain(mirror_path.resolve())`,
  the same one-line treatment `data_dir` gets. `graft` relocates rather
  than merges, so the spelling stays recoverable
  (`/var/mail/x` → `<root>/%2F/var/mail/x`) and a path already inside
  the root is returned untouched, which is why every existing fixture
  still resolves where it did.
  `tests/test_config.py::test_an_absolute_path_is_confined_to_pony_root`
  asserts containment; one existing test had to start expecting it, and
  the half-qualified refusal is unchanged (it is refused before any of
  this).

# 11. Work on the wrong thread

**The pattern.** A blocking call sits on the event loop because at the
size it was tested, it returned fast.

**How to spot it.** Any `async def` route that touches SQLite or the
filesystem without `run_in_threadpool`; any Textual handler that does
the same without a worker.

### 11.1 Blocking the event loop

- [x] **Every browser GET renders on the event loop, and there is no pagination** — `src/pony/web/app.py` (`_mail_page`, `_rows_fragment`, `_message_page`, `_attachment`, `_message_body`) · **time** · `[A]`

  Only `/action/*` and `compose.send` use `run_in_threadpool`.

  ```
  8,000 rows:  /mail      2384 KiB in 618 ms
               /mail/rows 2381 KiB in 496 ms
  ```

  50,000 rows extrapolates to ~15 MB and ~4 s during which the whole
  server is frozen: the other tab, an in-flight upload, the sync. And
  `refresh()` refetches the entire list after every single action.
  `_message_page` also does a SQLite **write** (`add_flag`) on the loop.

  The work is off the loop. Every one of those five renders, and the
  reads behind them -- the row list, the folder pane, a message's own
  bytes, its HTML, an attachment's part -- goes through
  `run_in_threadpool`, which is where `/action/*` and the send already
  were; the `add_flag` write went there in an earlier pass. A slow page
  is now this request's wait and nobody else's.
  `tests/test_web_app.py::test_a_slow_page_does_not_stop_the_other_tab`
  holds a render inside a `threading.Event` and requires a second
  request, on the same application, to come back while it is held --
  which on the event loop it could not, because nothing would resume to
  release it.

  Pagination was the decision that followed, and its owner made it:
  imitate the reader, which has always drawn a long folder in batches
  of `views.ROW_BATCH` with the event loop free between them. The page
  carries the first batch and the marker that says where the next one
  starts; the script follows the markers until there are none, and the
  marker is a link, so a page with no script reaches the rest by hand.
  The cursor question the note worried about did not arise: the cursor
  is keyed on the row the user is on, the marks are a set of message
  ids, and a refresh puts the first batch back and streams again --
  which is exactly what `load_folder` does in the terminal.
  `list_folder_message_summaries` takes the `limit` and `offset` in
  SQL, so a first screenful no longer materialises a folder of fifty
  thousand.

- [ ] **The message list's SQL fetch moved back onto the event loop** — `src/pony/tui/widgets/message_list.py:226` · **time** · `[R]`

  `list_folder_message_summaries` runs synchronously; only
  `DataTable.add_row` is streamed. `docs/architecture.md:347` says it
  "runs the SQL fetch in a Textual worker … so opening a 10k-row folder
  never freezes the event loop". That is no longer true, and unlike
  `list_folder_messages` this call has no `limit`.

  Left open deliberately, and the document no longer promises the
  worker (corrected in `15fc46b`). The straightforward move is unsafe:
  `load_folder` fills `self._summaries` and resolves
  `_restore_target` *synchronously*, and the screen reads
  `get_selected_summary()` immediately afterwards -- that is the
  contract `effective_cursor_row` exists to keep, and the one
  [§11.4](#114-cursor-state-read-raw-while-rows-stream) is about. Doing
  the fetch in a worker makes the panel momentarily empty, which is
  exactly the class of defect `main_screen.py:724` already is. What it
  wants is for the panel to own an "awaiting rows" state, with the
  cursor keyed on the message rather than the row, and then the fetch
  and the search below can both move. One piece of work, not two.

- [ ] **Search runs on the event loop in both front ends** — `src/pony/tui/screens/main_screen.py:835`; `chronos` `action_search` (which loads every component of every calendar) · **time** · `[R]`

  The 385 ms figure in `index_store.py:1010` is the documented cost.

  Left open with the item above, and for the same reason:
  `_show_search_results` is called by every action that changes a row,
  each of which reads the panel back immediately afterwards. The
  browser's half went off the loop with the rest of its rendering; the
  terminal's wants the panel's "awaiting rows" state first.

- [x] **Harvesting folder contacts loads the whole folder on the event loop** — `src/pony/tui/screens/main_screen.py:1841` · **time** · `[R]`

  `harvest_folder_contacts` is a worker now, awaiting
  `asyncio.to_thread`, which is the pattern `_apply_invitation` already
  used. Nothing reads the panel back from it -- what it produces is a
  notice -- so unlike the two items above there was nothing in the way.

### 11.2 Durability ordered the wrong way round

- [x] **The index commits before the mirror bytes are durable** — `src/pony/storage.py:114-150`; `src/pony/sync.py:1977` · **data** · `[R]`

  `store_message_async` hands the write to a pool and returns the
  filename; the row is indexed inside the folder's `connection()` and
  `flush_writes()` is called **after** the block. The ordering predates
  yesterday, but the per-500 commit changes what it costs: a
  mirror-write failure used to roll the whole folder back, and now the
  committed batches survive, leaving rows that name files which were
  never written. Only `check_mirror_integrity` (`services.py:340-370`),
  under `pony doctor`, detects it.

  Also: `_drain_pending` (`storage.py:146-150`) re-raises a failed write
  from inside `store_message_async`, so the error is attributed to
  whichever message is being stored at the time, not the one that
  failed.

  `flush_writes()` is inside the folder's transaction now, before the
  watermark: a write that failed after its row was written holds the
  folder back, so the next sync fetches those messages again instead of
  starting past a UID whose message never reached the disk. Rows
  already committed by an intermediate batch commit can still name a
  file that failed -- that is what batching costs, and the integrity
  scan is what finds it -- but the folder is re-synced rather than
  skipped.
  `tests/test_sync_execution_failures.py::test_a_write_that_failed_after_its_row_holds_the_watermark`
  makes the flush fail and requires no watermark.

  The attribution is fixed too: `_drain_pending` keeps the failure on
  the queue instead of raising it, and `flush_writes` -- the call whose
  contract is "every write is on disk, or you are told" -- raises it.

### 11.3 Cancellation that does not cancel

- [x] **Quitting `pony web` abandons a periodic sync mid-flight** — `src/pony/cli.py:2910-2948`; `src/chronos/scheduler.py:143-163` · **data** · `[R]`

  `PeriodicSync.stop()` joins for 5 s against a runner that explicitly
  swallows `cancel_event` ("A mail sync has no cancellation point"), then
  abandons the daemon thread. `grep -rn cancel_event src/pony/` returns
  nothing. A browser-initiated sync *is* waited for (uvicorn's graceful
  shutdown); the periodic one is not. `run_web`'s `finally` also never
  calls `index.close()`, so the last partial batch depends on `__del__`.
  No quit-while-syncing test exists.

- [x] **`_apply_invitation` cannot be cancelled mid-call** — `@work(exclusive=True)` around `asyncio.to_thread` · **suspected** · `[R]`

  Two trips through the dialog could file and reply twice.

  Confirmed by reading it again: `exclusive=True` cancels the worker,
  and the thread it is awaiting keeps going -- there is no cancellation
  point to offer inside an SMTP conversation. So the key refuses while
  one is in flight ("Still answering the last invitation.") rather than
  starting a second, which is the same shape `_sync_in_progress`
  already has.
  `tests/test_invitation_flows.py::test_a_second_answer_is_refused_while_the_first_is_in_flight`
  requires no dialog and a word about why.

### 11.4 Cursor state read raw while rows stream

- [x] **`move_cursor_to_next_unread` and `move_cursor_by` read `cursor_row`, not `effective_cursor_row`** — `src/pony/tui/widgets/message_list.py:370`, `:428` · **polish** · `[R]`

  Contradicting that property's own docstring ("Every caller that asks
  'which message is selected' has to see the destination"). Both are
  reached from the reader's `n`/`p`/`space` — exactly what a user
  presses right after a trash while rows are still streaming.

  Both read `effective_cursor_row` now.
  `tests/test_message_list_panel.py::test_n_and_space_move_from_where_the_cursor_is_going`
  puts the panel in the state `_load_rows` leaves between batches --
  the real cursor at 0, the destination pending -- and requires `n` to
  step from the destination and `space` to find nothing unread after
  it, where from row 0 it would have found the second row of the
  folder.

# 12. Operations outside the action modules

**The pattern.** The rule is that an operation lives over the stores and
returns an `Outcome`, so both front ends get it. Where the rule is
broken, the second front end silently lacks the feature — or, worse,
advertises it through the shared keymap and does something else.

**How to spot it.** For every key in `keymap.py`, ask what each front
end actually does with it.

### 12.1 A third front end nobody declared

- [x] **`pony calendar add` / `edit` creates an event no view can see** — `src/chronos/cli.py:1163`, `:1231`, `:1243` · **data** · `[A]`

  These call `ctx.index.upsert_component(...)` directly;
  `grep rebuild_caches src/chronos/cli.py` returns nothing.
  `event_actions.py:476-500` exists precisely for this and states the
  consequence: "without this the saved event vanishes from every view
  that joins `components` against `occurrences` (agenda, day, grid)
  until the next sync." Reproduced: occurrences after `calendar add` =
  0, after `save_event` = 1; `calendar edit` on a visible event takes
  it to 0.

  Pre-existing, not yesterday's work — but it is the clearest live
  instance of the rule the project wrote down. `chronos/cli.py` also
  reimplements `save_event`, `trash_event`, `organizer_for`
  (`cli.py:2184` is a byte copy of `event_actions.py:461`) and UID
  resolution, and `cmd_rm` trashes *every* calendar's copy of a UID
  where `trash_event` takes one component. Neither `src/pony/cli.py`
  nor `src/chronos/cli.py` imports a single action module.

  Fixed in `b6bae2a`: `cmd_add` and `cmd_edit` build an `EditDraft` and
  call `save_event`, `cmd_rm` calls `trash_event`, and the hand-written
  `organizer_for` is gone -- `chronos/cli.py` imports the action module
  now.
  `tests_calendar/test_cli.py::test_add_rebuilds_the_occurrence_cache`
  counts the occurrences the agenda joins against, which is what was
  zero.

  The `cmd_rm` half was still open and is now closed too: a UID two
  calendars hold is refused with the calendars named, as `show` and
  `edit` refuse it, instead of trashing both copies.
  `tests_calendar/test_cli.py::test_rm_refuses_a_uid_two_calendars_hold`
  requires both to survive.

### 12.2 Operations the browser cannot reach, and one the keymap lies about

- [x] **Saving an event with attendees from the browser invites nobody, silently** — `src/pony/tui/calendar_host.py:361`, `:419` · **data** · `[R]`

  `send_event_invitations` / `_with_method` are the entire
  Calendar→mail iTIP REQUEST path — pure model code, no Textual in it —
  in a module that imports `textual.app.App`. **Nothing in
  `pony/web` can reach it**, contradicting
  `docs/architecture.md → Invitations`.

- [x] **`s` means two different operations** — `src/pony/tui/screens/main_screen.py:1715` vs `src/pony/web/static/pony.js:465` · **trust** · `[R]`

  In the terminal `action_save_message` writes the body and attachments
  to a directory (Markdown conversion, `item.kind.split(":")[1]`
  parsing, an `is_relative_to` containment check, saved/failed
  counting). In the browser the same keymap entry downloads the raw
  `.eml`. Same key, same table, different operation.

  Settled by its owner: `s` saves the message as it arrived. A
  message is a numbered list of parts now -- `0` it, `T` its body as
  text with no HTML in it, `1..N` its attachments -- `pony/message_export.py`

# 13. Tests that cannot fail

**The pattern.** A test exercises the code path and asserts something
that was already true: that no exception escaped, that a string appears
in a source file, that a mock was called. It turns green and it stays
green when the feature is deleted.

This class is why several of the defects above shipped under a 92 %
coverage gate. Coverage measures *execution*, not *assertion*.

**How to spot it.** Replace the production method with `lambda: None`
and re-run the test. If it passes, it is not a test. Prefer asserting
against the store or the rendered output over asserting that a function
was reached.

  Both `run_worker(..., thread=True)` calls take Textual's default

  `app._handle_exception` and stops the app. `_on_plan_complete` and

  **Fix:** `exit_on_error=False` at both call sites. Fixed in
  `d8b2349`; the box went unticked until a recount.

# What the audits checked and found sound

Worth recording, because it bounds the problem.

- **The action modules are free of UI.** Across all 77 model-layer
  files: no `import textual`, no `app.notify`, no `query_one`, no
  `self.app`, no `Binding`, no `rich.`, no Starlette or uvicorn outside
  `cli.py`'s launch functions. Twenty of twenty-two mutations return an
  `Outcome` or a dataclass containing one.
- **`uid IS NULL` and `href IS NULL` each trace to exactly one SQL
  definition** — `src/pony/index_store.py:1170-1186` and
  `src/chronos/index_store.py:424`/`442` — with the planner as sole
  observer, as `protocols.py:390` promises. The overload is real
  (`uid IS NULL` carries six meanings, `href IS NULL` three) but the
  *signal* is single-homed: the ambiguity is in what writes it, not in
  who reads it.
- **`a36d9dd`'s defences work.** The APPEND/MOVE re-read, C-7, the
  unattended skip, the non-destructive C-4: several findings above stop
  at "and then the guard declines it".
- **`fb83cd9`'s producer/consumer is correctly bounded and cannot
  deadlock** — every wait is polled and bounded by
  `_PRODUCER_POLL_SECONDS` — and the phase split keeping the IMAP
  socket single-threaded is complete: every `SyncOp` case was checked
  for a `session` call.
- **`reindex`'s watermark is deliberately `uidnext=0`**, so a reindexed
  folder is structurally incapable of fast-pathing past missing rows.
- **The browser's HTML escaping holds** under a deliberate break-out
  payload on every path sender-controlled text can take.
- **The layering tests really do enforce rule 5**, `ef3ce05`'s
  divergence fixes landed in shared modules rather than being
  duplicated, and the `runServerAction` → `server` rename left exactly
  one deliberate reference, in a test docstring.
- **`FolderPolicy`, `trashed_copy`, the IMAP flag table, the
  fast/medium/slow path selection, `Outcome`/`Notice` construction and
  the profile stamping each exist once.** The
  `<synthetic-…@pony.local>` migration filter correctly targets only
  the dead v2-era prefix and not the live `<pony-copy-…>` one.
- **`tests/test_web_flows.py`, `tests/test_message_list_panel.py`,
  `tests/test_main_screen_io.py` and
  `tests/test_screens.py`'s contact-browser cases are the test
  discipline to copy** — they walk real links and assert against the
  stores. The link crawler's `len(seen) > 15` anti-vacuity guard earns
  its keep.

# 17. The browser front end does not behave like the reader

Found by using `pony web` on 2026-10-12, not by reading. The two front
ends share their operations, their keymap and their projections, so
where they diverge it is in the part each writes for itself — and that
part has had no audit of its own. Each of these is a user noticing that
the browser does something the terminal does not.

- [x] **Both panes lost their place on every click** — `src/pony/web/static/pony.js` · **time** · `[V]`

  Choosing a folder, opening a message and archiving one each threw the
  folder pane and the message list back to the top. Browsers restore
  scroll for history navigation only, never for a new URL, and all
  three are new URLs. Archiving the open message was worse: it left for
  the bare folder URL, so the reading pane emptied and the cursor went
  to the top. Fixed in `b941226` — positions remembered on `pagehide`,
  and an action that removes the open message follows on to whatever
  took its place.

  The terminal has the same cursor defect from the other direction, and
  it is already recorded: `main_screen.py:724`'s cursor-restore after
  `_reload_folder` cannot fire, because `load_folder` streams rows from
  a worker and `row_count` is still 0 on the next line. Trash and
  archive send the cursor to the top there too.

- [x] **A confirmation is the browser's dialog, in the browser's words** — `src/pony/web/static/pony.js:320`, `:550` · **polish** · `[V]`

  Both confirmations call `window.confirm`, so the question is Pony's
  and the buttons are the browser's: a Spanish-locale browser offers
  "Aceptar" and "Cancelar" under "Discard this message? Use Save draft
  to keep it." The reader names its buttons after what they do
  (`ConfirmScreen`, `SaveDraftScreen`), and a confirmation whose
  buttons do not match its question is the one place a user cannot
  afford to guess.

  `pony.js` already builds a styled `<dialog>` for prompts (`ask()`),
  so the shape to copy is in the file.

  The defect is sharper than the locale. The question names a button it
  cannot offer — "Use Save draft to keep it" points at a control the
  modal is covering — and dismissing the modal is itself one of the two
  answers, so a boolean replacement for `confirm()` would not have
  fixed it. And a browser that has been told to stop a page opening
  dialogs returns `false` with no UI at all: on the held-sync path that
  is a sync that declines itself in silence, every time.

  `choose()` is `ask()`'s shape for a question answered by choosing: it
  resolves *which* answer, so leaving a dirty form offers Save draft
  (or Save), Discard and Cancel, as `SaveDraftScreen` does, and a held
  action offers Proceed and Cancel, as `SyncConfirmScreen` does.
  Saving presses the button that files the form, so the server gets
  what that button names. Enter takes the default, Escape cancels,
  `Y`/`N` are the reader's own, and a press inside the dialog reaches
  nothing underneath. `notify()` still runs before the question, so the
  explanation is painted with it rather than behind it.

  `tests/test_web_browser.py::test_a_held_action_is_confirmed_in_ponys_own_dialog`
  drives it in Chromium — which is possible only because it is a
  `<dialog>`: a native `confirm` blocks the page and the `--dump-dom`
  harness with it, and that is exactly why the one assertion there was
  for the literal string `window.confirm`.

- [x] **`mailto:` in a message body leaves Pony** — `src/pony/web/mail.py:590` · **polish** · `[V]`

  The link is rendered as a plain `mailto:` anchor, so clicking it
  hands the address to whatever the operating system has registered —
  which is not the mail program the user is reading in. The terminal
  routes the same link to its own composer (`action_compose_link`,
  `LinkActionScreen`). The browser should open `/compose?to=…`.

  It does now, built on the server — the pages work with the script off
  — and it carries the message's own folder, so the draft starts on the
  account the mail arrived at.
  `tests/test_web_app.py::test_an_address_in_a_body_opens_the_composer_and_not_the_desktop`
  follows the link off the page and reads the prefilled form back.

- [x] **No way to keep an address from the browser** — `src/pony/web/contacts.py` · **polish** · `[V]`

  The contacts pages list and edit, but nothing adds: there is no `(+)`
  for recording an address and a name, so a correspondent met in the
  browser cannot be kept without going to the terminal. The reader
  harvests from a folder and offers the contacts browser; the browser
  front end has the pages but not the entry point.

  **The claim is wrong.** The list's heading carries a `New` link to
  the blank form, beside Delete marked and Merge marked
  (`contacts.py:_tools`); `c` is served to the browser for the same
  thing; and `H` harvests a folder there as it does in the terminal.
  What was missing is a test that the entry point is on the page, which
  is why reading the module could suggest otherwise:
  `tests/test_web_contacts.py::test_the_list_leads_to_the_blank_form_without_a_keyboard`
  now walks it, by the link's own label.

**The general point, which outlives these four items.** Parity between
the two front ends is asserted by `tests/test_keymap.py` for keys and
by `tests/test_web_dispatch.py` for what a key can do, and by nothing
at all for what the user experiences: where the cursor goes, what keeps
its place, which dialog appears and in whose words. Every item above
got past both of those tests. Worth a pass of its own, walking the
reader's common paths in the browser and writing down each difference.

- [x] **The account name was smaller than the folders under it** — `src/pony/web/static/pony.css` · **polish** · `[V]`

  `#folders h2` carried `font-size: 0.78rem` while a `.folder`
  inherits the body's `0.9375rem`, so the thing naming the section read
  as smaller than its contents; the reader's panel gives an account the
  same size as its folders. Fixed by deleting the declaration rather
  than adding another, so the heading inherits.

- [x] **The folder tree has no hierarchy to see** — `src/pony/web/static/pony.css` (`.tree .tree`), `src/pony/web/mail.py:_folder_nodes` · **polish** · `[V]`

  Nesting is expressed as `padding-left: 0.9rem` and nothing else. The
  reader draws guide lines, so which folders belong to which account
  and which descend from which parent is visible at a glance; in the
  browser a deep tree is a column of indented names. The markup is
  already nested `<ul>`s, so this is a border on the nested list rather
  than new structure.

  A `border-left` on `.tree .tree`, where the indent already was.
  `tests/test_web_browser.py::test_the_folder_tree_folds_and_shows_what_descends_from_what`
  reads the computed `border-left-width` of a nested list in Chromium,
  and the left edge of a parent's name against a leaf's at the same
  depth: the fold's twisty sits in the gutter every other row leaves
  empty, so the names line up either way.

- [x] **Nothing folds** — `src/pony/web/static/pony.js:957` · **polish** · `[V]`

  The reader folds an account and folds a parent folder, which is how
  a dozen accounts stay usable. The browser has no fold at all:
  `wireFolderToggle` is named for it but is the phone layout's
  show-the-whole-pane toggle, bound to the status line. A `<details>`
  per account and per parent would need no script, which is the same
  answer the sender panel reached.

  A `<details>` per account, and one per folder that has folders under
  it, whose summary is the folder's own row: the name still opens the
  folder — a link inside a summary navigates and does not toggle, which
  the browser test executes — and the twisty beside it shows or hides
  what is below. No script is needed for the fold itself. What the
  script adds is memory, beside the pane positions and on the same
  occasion: choosing a folder is a new URL, so the tree is built again
  with everything open, and a fold would be undone by the click after
  it. `rememberFolds` on `pagehide`, `restoreFolds` on load, keyed by
  the account and the labels down to the node — the labels rather than
  the stored folder name, because the server's delimiter may be a dot
  and a synthetic level has no stored name at all.

- [ ] **A refresh fetches two fragments where one would do** — `src/pony/web/static/pony.js:492`, `:541` · **time** · `[V]`

  Every action repaints by fetching `/mail/rows`, swapping it, then
  fetching `/folders` and swapping that -- two round trips, and the
  second does not start until the first has landed, because it is a
  second `await` in the same function. The unread counts beside the
  folders are a projection of the same query the rows come from, so a
  server that answered both in one response would halve the latency of
  every archive and every mark-as-read, and remove the window in which
  the list and the counts disagree. It sits beside §11.1: what the
  browser pays there is the render, what it pays here is the second
  trip.

**How far the pages work with no script at all.** Worth writing down,
because it has been overstated in both directions. Links work: every
folder, message, page of the calendar and the `New` of the address book
is an `<a href>` the server builds, and the compose form is a
`method="post"`, so reading, navigating and sending all work with
script off. The folds work, being `<details>`. What does not is the
action bar: the buttons are `<button type="button" data-action>` and do
nothing without the dispatcher -- by design, since `A` and `T` are
`POST /action/*` and the page would need a form per button to submit
one. So the no-script page reads and sends mail and cannot file it.
That is a deliberate line, not a gap, and the only thing missing is
that nothing says so where a reader of `web/app.py` would find it.

**On the stylesheet itself.** The three items above, the `.unread`
collision in `937829e` and the weight churn in `bb896d9`/`b4cc41d` are
one finding: `pony.css` sets per-element values -- `0.78rem`,
`0.8rem`, `0.85rem`, `0.95rem`, `0.75rem` -- where it should be
deriving from a few named steps, and reaches for bare class selectors
that collide with state classes the markup also uses. Nothing is
individually wrong, which is why each of these needed a user to notice
it. The fix is a pass over the file to establish a type scale and a
spacing scale, scope every selector to the pane it belongs to, and
delete whatever then says nothing new -- not another local override.
